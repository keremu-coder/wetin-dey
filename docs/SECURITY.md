# Security model — Wetin Dey

This document describes the security posture that is actually implemented,
including deliberate trade-offs and their rationale. It exists so future
contributors (and future audits) do not have to re-derive decisions from
code archaeology.

Last meaningful revision: October 2026, following the hostile audit
sections 1–4. All findings through M14, H12, and M1 are closed or
explicitly deferred below.

---

## 1. Sessions

### Cookie format

    current:  <session_id>.<epoch>.<hmac(session_id:epoch)>
    legacy:   <session_id>.<hmac(session_id)>   (accepted, treated as epoch 1)

- HMAC-SHA256, constant-time comparison, `SESSION_SECRET` (>= 32 chars,
  required — the process throws at startup if missing).
- `httpOnly: true`, `sameSite: "lax"`, `secure` only in production,
  `maxAge: 90 days`.
- Implemented in `lib/session.ts`.

### Revocation (epoch)

Every session row carries a `session_epoch` integer (migration 026). The
cookie MAC binds the epoch, so an attacker cannot forge a different value.

`bumpSessionEpoch(sid)` increments the stored epoch. Any cookie issued
before the bump fails the epoch check in `getSessionId()` and is treated
as unauthenticated. Bumps fire on:

- `/api/auth/signout`
- `/api/auth/reset-password` (for every session on that auth user)
- `/api/settings/recovery-code` (rotation is a security event)

### Epoch cache window (accepted limitation)

`getSessionId()` caches the DB epoch for **30 seconds per server
instance** (`EPOCH_CACHE_TTL_MS` in `lib/session.ts`). This means a
stolen cookie can continue to authenticate against a warm Vercel
instance for up to 30s after revocation.

Accepted because:
- The theft threat model requires the attacker to already possess the
  cookie.
- The alternative (a DB read per authenticated call) costs ~5–10ms per
  request on every warm path.

If "instant logout everywhere" ever becomes a product requirement, drop
the cache TTL or add an explicit pub/sub invalidation channel.

## 2. Ban model

Two independent bans:

**Session ban** — `sessions.banned_at` + `ban_reason`. Enforced by
`isBanned()` / `assertNotBanned()` (`lib/ban-guard.ts`, `lib/guards.ts`),
called at the top of every write route. Banned users can still read.

**IP-hash ban** — `banned_ip_hashes` (migration 028). When an admin bans
a session, that session's `last_ip_hash` (salted SHA-256 of the inbound
IP at session-creation time) is recorded with a 30-day expiry. New
*anonymous* session creation is refused from a banned IP.

### Escape hatch

Named signup (`/api/join`) passes `bypassIpBan: true`. A banned user
willing to verify an email can always rejoin. Accountability replaces
anonymity.

### Known limits (deliberate, not bugs)

- VPN / proxy rotation defeats the IP ban.
- Mobile carrier CGNAT rotation (airplane mode) defeats it.
- Shared IPs (cafés, hostels, university NAT) get false positives for
  the 30-day window. Bounded by the named-signup escape.

The IP ban is a **speed bump**, not a wall. Its real value is stopping
the common "clear cookies, retry from the same WiFi" case.

## 3. Fail-open behaviors (accepted, monitored)

Three subsystems fail open by design. Each is a trade-off between
availability and the specific risk, and each is documented at its call
site:

| Subsystem | Failure mode | Rationale |
|---|---|---|
| `getBlockedIds` (`lib/blocks.ts`) | Returns empty Set on DB error | Blocking failures should not blank the entire feed. Logged; alerting should catch sustained rates. |
| Moderation classifiers (Groq / Whisper) | Content proceeds without classification | A model outage should not silence legitimate civic reports. Humans compensate via the review queue. |
| `readRequestIpHash` (`lib/session.ts`) | Returns null on error | IP ban check is skipped rather than blocking legitimate new sessions. |

None of these should be "fixed" to fail closed without revisiting the
rationale above.

## 4. Recovery codes

- Format: human-readable, generated by `generateRecoveryCode()`.
- Storage: HMAC-SHA256 hash only (`hashRecoveryCode`), column
  `sessions.recovery_code_hash`, unique index on non-null values.
- Secret: `RECOVERY_HASH_SECRET`. **Rotating this invalidates every
  existing recovery code** — plan a rotation flow before changing it.
- Plaintext is shown to the user exactly once at creation. It is never
  recoverable from the DB.

## 5. RLS posture

**Application code is the primary access-control layer.** All route
handlers use the service-role Supabase client and enforce checks
explicitly (session lookup, `isBanned`, `hasAcceptedTerms`, ownership,
rate limits). RLS is a defensive backstop, not the primary mechanism.

This is a deliberate architecture choice. It requires discipline: every
new write route must include the standard guard sequence. A CI smoke
test that probes key routes with an anon key would catch regressions —
see "Open items" below.

Migration 029 dropped stale `*_insert_anon` policies on
`reports/comments/flags/disputes/me_toos` and the wide-open
`sessions_read_public`. These were already inert (grants revoked in
migration 013) but presented a landmine if any future migration
re-granted INSERT or SELECT.

## 6. Data handling

### PII present in the DB

| Field | Table | Protection |
|---|---|---|
| `email` | `sessions` | Plaintext, needed for auth. Never logged. |
| `phone` | `sessions` | Plaintext, optional. Never logged. |
| `recovery_code_hash` | `sessions` | HMAC-SHA256. |
| `last_ip_hash` | `sessions` | Salted SHA-256 (`SUPABASE_SERVICE_ROLE_KEY` as salt). |
| Message bodies, reports | various | Plaintext, user-generated, visible per app rules. |

### Deletion

`/api/account/delete` removes the session row and its identifying fields.
Reports and comments that comply with the content rules remain in the
public archive as anonymized content (per the retention promise in
`/privacy`). Voice-note files are removed from storage (H6, shipped
October 2026).

### Export

Currently **manual via support@wetindey.app**. The support process must
verify identity before delivering any export. An authenticated,
self-service export flow is a roadmap item; if shipped, the delivery
target must be the verified email on the account, never a
user-supplied address.

## 7. Secrets inventory

All required in Vercel production (verified October 2026):

| Secret | Purpose | Rotation impact |
|---|---|---|
| `SESSION_SECRET` | HMAC for session cookies | Rotating logs out every user. |
| `SUPABASE_SERVICE_ROLE_KEY` | Service-role DB access + IP hash salt | Rotating the DB key requires redeploy; also rotates IP-hash values (rate-limit buckets reset). |
| `RECOVERY_HASH_SECRET` | HMAC for recovery codes | Rotating invalidates every recovery code. |
| `CRON_SECRET` | Auth for `/api/radar/sweep`, `/api/mirror`, `/api/archive/export` | Rotating requires updating GitHub Actions + Vercel cron config. |
| `FCM_SERVICE_ACCOUNT_JSON` | Firebase Cloud Messaging | Rotating requires regenerating the service account JSON in Firebase console. |
| `VAPID_PRIVATE_KEY` / `NEXT_PUBLIC_VAPID_PUBLIC_KEY` | Web push | Rotating invalidates every web push subscription. |
| `NEXT_PUBLIC_SUPABASE_URL` / `NEXT_PUBLIC_SUPABASE_ANON_KEY` | Client Supabase access | Public by design. |

Never log or echo any of these. `console.error` calls that might receive
an error object must not include the secret itself — check any future
changes against this rule.

## 8. Open items

Not yet shipped, tracked here so they are not lost:

- **CI smoke test** for anon-key probing (would catch a future
  migration that re-grants anon INSERT/SELECT).
- **Observability**: HMAC failure rate, moderation-service error rate,
  and epoch-bump failure rate are logged but not alerted on. Sentry (or
  equivalent) is the recommended addition.
- **Self-service data export** with verified-email delivery (currently
  manual via support email).
- **iOS background geolocation SPM plugin** — blocked on an Apple
  Developer account. See `docs/APP-REVIEW-NOTES.md` for the roadmap
  position.
